Tudela Global MVP technical specification

Version 1, 13 October 2026. This is the current specification for the rebuild from Build 1.zip. Earlier documents in this folder describe the previous architecture and are retained as reference, not instructions for this MVP.

What the app does

Tudela helps visitors discover Jewish heritage, choose a city and tour, read and listen to stories at individual stops, and open Google Maps for walking directions. Staff create and review tours in a separate editing area. Visitors can save content and, once shared accounts are configured, contribute ratings, comments and personal stories.

Budapest is the first European pilot. Existing cities and sample tours remain available. An MVP means a testable product with a deliberately small operating model; it does not mean that placeholders are presented as working online services.

Rules for this rebuild

1. The initial operating target is as close to zero budget as practical. No paid service is activated by this rebuild.

2. Tudela does not call an AI API, send prompts automatically, or display generated answers as if they came from its own assistant. The visitor copies a prompt and opens their own AI website.

3. Google Maps provides external maps and navigation. An in-app Google map is optional and requires a separate configuration decision.

4. Shared personal data belongs to the signed-in account. A visitor must never receive another account's private notes.

5. Only reviewed and published content is served from the shared catalogue. Bundled sample content is labeled as demonstration content.

6. Existing source code is reused where it supports these rules. Source files and archived feature claims alone are not proof that a feature has passed live testing.

How the pieces fit together

The visitor interface is a React website: it can be used on a phone or desktop and supports installation as a web app. A small Express server serves the website and checks requests. Supabase supplies the shared database, account sign-in and file storage when configured. Its local version can run on the developer's machine; no paid hosting is needed to demonstrate the visitor experience.

The browser stores visitor preferences, cached tour content and saved content for local use. Google Maps and the user's AI service open separately. Tudela cannot observe or control what happens inside those services.

Local address: http://localhost:3220. Staff editing area: http://localhost:3220/cms. This specification and the plan are available through http://localhost:3220/mvp-guide.

AI use step by step

The visitor writes a question and selects ChatGPT, Gemini or Claude. Tudela prepares a visible text prompt naming the selected city and asking for sources and clear uncertainty. The visitor chooses Copy prompt, opens the selected service and pastes the prompt into their own conversation. Their service may require sign-in, impose a free-use limit or offer paid subscriptions.

Tudela does not transfer GPS, account credentials or private notes with the prompt. It does not automatically read the answer, save it or publish it. If AI-assisted material is later used to author a tour, a person must bring it back as a draft, check facts, confirm media rights and submit it to the normal review process.

The old AI and narration provider source files remain historical code in the recovered project; the running MVP does not expose a route that invokes them. Adding API keys does not enable AI calls in this server.

Google Maps and cost choices

The default uses standard Google Maps URLs for a stop pin, walking navigation and nearby search. These URLs need no API key. Google receives the destination and, only when explicitly included for a directions link, the origin. The user can continue using Google Maps independently of Tudela.

An optional Maps Embed API map can display the current stop inside Tudela. Google lists Embed usage as no charge, but requires an API key and a billing-enabled project. It is off by default. Interactive custom maps, live place search, geocoding and route calculations are different products and can incur usage charges; they are not included in the zero-budget MVP. Spending alerts alone are not a guaranteed spending cap.

Data and permissions in plain language

An organization owns its cities, tours, stops, translations, files and publishing records. A membership gives an account a role in that organization. Visitor contributions record who submitted them. Review records identify who approved or rejected them. Published records are separated from drafts.

Private sync data is stored under the signed-in account ID. The database has an owner-only rule, and the server checks the token before reading or saving it. Anonymous users cannot read or write shared notes. This change replaces the old global memory store. Cross-device retrieval and conflict handling must be tested in the shared-service stage.

Local storage can be accessed by another person using the same browser profile. Do not use private notes for sensitive personal information on a shared device. Logout behavior and device-data removal are part of the pilot privacy checks.

What counts as complete

A working screen is not the same as a verified service. The development plan records each stage as implemented, locally tested, awaiting configuration or pending. The visitor stage must build successfully and pass its applicable logic checks. The account and publishing stage must pass real database tests, including a test that one account and organization cannot access another's private data.

Phone testing must cover GPS denial, loss of connection, audio playback, Hebrew layout, large text, a completed tour and Google Maps handoff. A public pilot also needs reviewed content, media permission, a tested backup and a chosen hosting budget. No paid upgrade is assumed.

Tudela Global MVP staged development plan

Version 1, 13 October 2026. First pilot: Budapest. Budget target: zero new service spending during local development. Each stage updates the technical specification and verification log before being called complete.

Starting position

Build 1.zip contains a substantial React visitor app, an Express server, a staff CMS, Supabase migrations and feature checks. It is ahead of a blank prototype. Previous production documents and test reports describe the earlier build and are not proof that this restored copy is deployed or verified.

The rebuild keeps that investment and changes three architectural choices: AI opens the visitor's own service, Google Maps navigation uses external links, and account sync is authenticated and private. Do not estimate completion from source-file count.

Stage 1 Restore and establish the baseline

Deliverables: isolated Tudela project, locked dependencies, feature inventory, local start command, a build result and a first verification log. Keep SubFinder and its GitHub repository separate. Do not run archived deployment or backup scripts as part of extraction.

Completion gate: the restored app builds and its source can be inspected without live keys. Identify any baseline failures and database-dependent tests separately.

Stage 2 Apply the zero budget operating model

Deliverables: copy-and-open personal AI workflow; Google Maps stop search and walking navigation; disabled AI, generated narration, paid Routes, paid Places and automatic geocoding endpoints; owner-protected visitor sync; updated privacy disclosure and service budget.

Completion gate: automated checks prove AI endpoints cannot generate responses, no paid map request is made, malformed coordinates are rejected, and anonymous sync cannot read or write notes. A test must confirm that adding legacy AI keys does not activate the old runtime.

Stage 3 Demonstrate the visitor MVP

Deliverables: Budapest discovery and ordered tour stops; stop details; saved content and notes; recorded or device audio; location controls; offline behavior; personal AI handoff; clear demonstration-content labels. Keep the existing cities available.

Completion gate: run a tour from selection to completion on desktop and a phone. Confirm GPS permission denial is handled, simulated GPS is labeled, Google Maps opens the correct stop, and audio can be paused. Offline mode must not claim offline maps or AI. List any unverified phone behavior.

Stage 4 Connect accounts and the shared database

Deliverables: configured local Supabase, applied migrations including visitor_state, owner bootstrap, sign-up and login, password-recovery development flow, private sync, published catalogue and media storage. If local infrastructure is impractical, discuss the free hosted plan's limits before provisioning it.

Completion gate: database migrations and row-permission tests pass. Two test accounts must be isolated; two organizations must be isolated. Guest access must expose published content only. Demonstrate save and retrieve using a real account. Document credentials setup without publishing secrets.

Current external dependency: Docker Desktop's engine is not running. It is not a code-completion gate for visitor demos, but it blocks verification of a local shared database.

Stage 5 Verify content authoring and publishing

Deliverables: city, tour and stop editing; multilingual transcripts; manual coordinates; image and recording uploads; source records; draft import; review, revisions, publish, archive and restore. Visitor suggestions must become drafts for review rather than publishing themselves.

Completion gate: an editor creates a Budapest tour, a reviewer requests and approves a correction, and permitted staff publish it. The visitor sees only the approved version. An editor must not gain reviewer permissions by changing a request. Check file type, size and rights metadata.

Stage 6 Verify community and offline behavior

Deliverables: ratings, moderated comments, likes, share links, heritage stories, banning, saved-tour recovery, device preferences and account isolation. Implement or correct any gaps revealed by real database tests.

Completion gate: comments and stories are not public before approval; account restrictions apply; cached content remains useful after connection loss. Sync conflicts and deletion have a documented behavior. No hidden global notes store remains.

Stage 7 Prepare a small real visitor pilot

Deliverables: historical and coordinate review, cleared media, translated revised screens, accessible mobile testing, privacy and support wording, backups and one pilot tour. Validate practical venue information with current official sources.

Completion gate: at least one complete on-location pilot is reviewed, critical issues are corrected and a restore test succeeds. Update the guide so a nontechnical tester can run the tour without developer assistance.

Stage 8 Choose public hosting only when needed

Deliverables: an explicit hosting decision and budget, HTTPS, provider configuration, health monitoring and deployment procedure. No migration to paid services without a cost discussion. Public availability is a separate deliverable from pushing source to GitHub.

Completion gate: confirm free-plan eligibility and actual caps, sleep behavior, account-email delivery and storage growth. If a free plan cannot support the agreed pilot, record the limitation and cheapest viable alternative before changing the operating model.

Order and progress reporting

Work through Stages 1–3 immediately using local and bundled data. Stages 4–6 reuse the archived schema and CMS instead of rewriting them. Stage 7 follows once shared service behavior is verified. Stage 8 is a budget decision, not an automatic action.

After each meaningful change, update MVP-Technical-Spec.md, MVP-Verification.md and the feature inventory. State what passed, what needs keys or infrastructure, and what a tester can try now. There is no fixed completion percentage until all gates have evidence.
